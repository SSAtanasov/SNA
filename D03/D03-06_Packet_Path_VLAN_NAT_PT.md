# D03-06: Пътят на пакета през мрежите – маршрутизиране, VLAN и NAT (Packet Tracer, PDU)

> **Поток:** КСК | **Време:** ~90 мин | **Среда:** Packet Tracer 8.2.2
> **Задължителен минимум:** Части 1–3. **Разширение:** Части 4 и 5.
> **Връзка с курса:** лекции D03-02 (маршрутизиране, комутатор срещу маршрутизатор), D02-03 (IPv4, NAT), D02-02 (Ethernet, MAC) и D02-01 (мрежов дизайн); семинари D02-02 (VLAN) и D02-08 (NAT) при потока АКС + ИКТО.

## ПРЕДИ УПРАЖНЕНИЕТО

**За справка:** записките към лекциите [D03-02](../res/D03-02.md) (маршрутизиране, шлюз по подразбиране, комутатор срещу маршрутизатор), [D02-03](../res/D02-03.md) (NAT, частни адреси) и [D02-02](../res/D02-02.md) (MAC адреси).

**Защо ни трябва:** Тук се вижда защо е нужна маршрутизация: пакетът стига до друга мрежа само през маршрутизатор, а адресите в него се сменят по точни правила.

**Какво трябва да видите в упражнението:** Нова рамка с нови MAC адреси на всеки сегмент; непроменени IP адреси до границата; сменен source адрес и порт след NAT.

### Комутатор срещу маршрутизатор

| | Комутатор | Маршрутизатор |
|---|---|---|
| Слой | L2 | L3 |
| Решение по | destination MAC адрес (MAC таблица) | destination IP адрес (таблица за маршрутизиране) |
| Broadcast | препраща го на всички портове | не го препраща – разделя broadcast домейните |
| Свързва | устройства в една мрежа | различни мрежи |

**Маршрутизиране между VLAN** работи по същия принцип. При „маршрутизатор на пръчка“ (router-on-a-stick) една физическа връзка носи няколко VLAN, а маршрутизаторът има по един подинтерфейс за всяка VLAN. Пакетът от VLAN 10 към VLAN 20 влиза и излиза през един и същ физически порт, но с различен етикет 802.1Q и с нови MAC адреси – точно както при два отделни интерфейса.

### Проверете се

1. Кои адреси в пакета се сменят на маршрутизатора без NAT и кои остават същите?
2. Защо два компютъра в различни VLAN на един комутатор не могат да си говорят без маршрутизатор?
3. Какво сменя PAT в изходящия пакет?

## Цели на упражнението

- Проследяване на един и същ пакет през няколко мрежи в режим Simulation
- Установяване кои адреси се сменят на всеки преход (hop) и кои се запазват
- Наблюдаване на ARP в отделните сегменти
- Наблюдаване на транслацията на адреса на изхода през NAT (PAT)

## Теоретична основа

Когато пакетът преминава от една мрежа в друга:

- **MAC адресите се сменят на всеки сегмент.** Всеки маршрутизатор изгражда нова Ethernet рамка: source е неговият изходящ интерфейс, destination е следващото устройство.
- **IP адресите при обикновена маршрутизация се запазват** от източника до целта.
- **TTL намалява** с 1 на всеки маршрутизатор.
- **NAT** е изключение: маршрутизаторът на границата сменя частния **source** IP адрес (Inside Local) с публичен (Inside Global). При PAT (overload) се сменя и source портът, ако е нужно, а за ICMP – идентификаторът.


## Топология

Изградете следната минимална топология (опростен вариант на мрежата от семинар D02-08 при потока АКС + ИКТО):

```
 PC0 ──── SW0 ──── R1 ═══════════ R2 ──── Server0
 192.168.1.10      G0/0  G0/1   G0/0  G0/1      198.51.100.10
 GW .1           .1/24   .1/30  .2/30  .1/24     GW 198.51.100.1
                 (inside) (outside)
```

| Устройство | Интерфейс | IP адрес / маска | Шлюз |
|------------|-----------|------------------|------|
| PC0 | Fa0 | 192.168.1.10/24 | 192.168.1.1 |
| R1 (2911) | G0/0 | 192.168.1.1/24 (NAT inside) | – |
| R1 (2911) | G0/1 | 203.0.113.1/30 (NAT outside) | – |
| R2 (2911) | G0/0 | 203.0.113.2/30 | – |
| R2 (2911) | G0/1 | 198.51.100.1/24 | – |
| Server0 | Fa0 | 198.51.100.10/24 | 198.51.100.1 |

**Кабели:** PC0–SW0 и SW0–R1 – Copper Straight-Through; R1–R2 и R2–Server0 – **Copper Cross-Over**.

> Мрежите 203.0.113.0/24 и 198.51.100.0/24 са запазени за документация и тук играят ролята на „Интернет“.

**Конфигурация на R1:**

```
R1(config)# interface g0/0
R1(config-if)# ip address 192.168.1.1 255.255.255.0
R1(config-if)# ip nat inside
R1(config-if)# no shutdown
R1(config-if)# interface g0/1
R1(config-if)# ip address 203.0.113.1 255.255.255.252
R1(config-if)# ip nat outside
R1(config-if)# no shutdown
R1(config-if)# exit
R1(config)# access-list 1 permit 192.168.1.0 0.0.0.255
R1(config)# ip nat inside source list 1 interface g0/1 overload
R1(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.2
```

**Конфигурация на R2:**

```
R2(config)# interface g0/0
R2(config-if)# ip address 203.0.113.2 255.255.255.252
R2(config-if)# no shutdown
R2(config-if)# interface g0/1
R2(config-if)# ip address 198.51.100.1 255.255.255.0
R2(config-if)# no shutdown
```

> R2 не се нуждае от маршрут към 192.168.1.0/24: след NAT пакетите идват от 203.0.113.1, а тази мрежа е директно свързана с R2. Помислете какво би станало без NAT.

## Част 1: Подготовка

**a.** Проверете връзката в режим **Realtime**: от PC0 изпълнете `ping 198.51.100.10`. Ако първите отговори изтекат (Request timed out), повторете – това е времето за ARP.

**b.** Изчистете кешовете, за да видите целия процес:
- на PC0: `arp -d`
- на R1 и R2: `clear arp-cache`
- на R1: `clear ip nat translation *`

**c.** Превключете в режим **Simulation**. В **Edit Filters** оставете само **ARP** и **ICMP**.

> **Предвидете:** Попълнете колоната „Очакване“ в таблицата от Част 2, преди да пуснете пакета.

## Част 3: Echo Reply и таблицата на NAT

**a.** Продължете с **Capture/Forward**, докато Echo Reply се върне до PC0. Попълнете:

| Сегмент | Src IP | Dst IP | Src MAC | Dst MAC |
|---------|--------|--------|---------|---------|
| Server0 → R2 | | | | |
| R2 → R1 | | | | |
| R1 → PC0 | | | | |

**b.** Превключете в **Realtime** и на R1 изпълнете:

```

```

Попълнете реда за ICMP:

| Pro | Inside global | Inside local | Outside local | Outside global |
|-----|---------------|--------------|---------------|----------------|
| icmp | | | | |

- _На кой адрес отговаря Server0 – на 192.168.1.10 или на 203.0.113.1? Защо?_ ______
- _Как R1 разбира, че Echo Reply е за PC0?_ ______

<details markdown="1">
<summary>Отговори за самопроверка</summary>

- ARP има в трите сегмента: PC0 търси MAC на 192.168.1.1, R1 търси MAC на 203.0.113.2, R2 търси MAC на 198.51.100.10.
- Между първия и втория сегмент R1 сменя и двата MAC адреса, **и** source IP: 192.168.1.10 → 203.0.113.1 (NAT). Destination IP остава 198.51.100.10.
- Между втория и третия сегмент R2 сменя само MAC адресите; IP адресите остават.
- TTL намалява с 2 (два маршрутизатора).
- Server0 отговаря на **203.0.113.1** – той не вижда частния адрес. R1 намира в NAT таблицата записа с Inside global 203.0.113.1 и идентификатора на ICMP и връща destination на 192.168.1.10.

</details>

## Част 5 (разширение): Маршрутизиране между VLAN и етикетът 802.1Q

В тази част локалната мрежа зад R1 се разделя на две VLAN. R1 маршрутизира между тях през **една** физическа връзка (router-on-a-stick). Целта е да видите в PDU етикета 802.1Q и да потвърдите, че правилата от Част 2 (сменят се MAC адресите, а IP адресите се запазват) важат и тук.

### Стъпка 1: Добавяне на втори компютър

**a.** Добавете **PC1** и го свържете към SW0. Задайте `192.168.2.10/24`, шлюз `192.168.2.1`.

**b.** Задръжте курсора върху връзките, за да видите номерата на портовете на SW0: към PC0, към PC1 и към R1.

### Стъпка 2: VLAN на комутатора

Заменете `Fa0/1`, `Fa0/2` и `Gi0/1` с вашите портове от Стъпка 1:

```
SW0(config)# vlan 10
SW0(config-vlan)# vlan 20
SW0(config-vlan)# exit
SW0(config)# interface fa0/1
SW0(config-if)# switchport mode access
SW0(config-if)# switchport access vlan 10
SW0(config-if)# interface fa0/2
SW0(config-if)# switchport mode access
SW0(config-if)# switchport access vlan 20
SW0(config-if)# interface gi0/1
SW0(config-if)# switchport mode trunk
```

`Fa0/1` е портът към PC0, `Fa0/2` – към PC1, `Gi0/1` – към R1.

### Стъпка 3: Подинтерфейси на R1

```
R1(config)# interface g0/0
R1(config-if)# no ip nat inside
R1(config-if)# no ip address
R1(config-if)# interface g0/0.10
R1(config-subif)# encapsulation dot1Q 10
R1(config-subif)# ip address 192.168.1.1 255.255.255.0
R1(config-subif)# ip nat inside
R1(config-subif)# interface g0/0.20
R1(config-subif)# encapsulation dot1Q 20
R1(config-subif)# ip address 192.168.2.1 255.255.255.0
R1(config-subif)# ip nat inside
R1(config-subif)# exit
R1(config)# access-list 1 permit 192.168.2.0 0.0.0.255
```

### Стъпка 4: Наблюдение в Simulation

**a.** В режим **Simulation** с филтри **ARP** и **ICMP** изпълнете от PC0 `ping -n 1 192.168.2.10`.

**b.** Проследете Echo Request и попълнете:

| Сегмент | VLAN етикет (802.1Q) | Src MAC | Dst MAC | Src IP | Dst IP |
|---------|----------------------|---------|---------|--------|--------|
| PC0 → SW0 | | | | | |
| SW0 → R1 (trunk) | | | | | |
| R1 → SW0 (trunk) | | | | | |
| SW0 → PC1 | | | | | |

- _На кои сегменти рамката носи етикет 802.1Q и с какъв номер на VLAN?_ ______
- _Колко пъти пакетът минава през връзката SW0–R1 и с какви етикети?_ ______
- _Извършва ли R1 NAT за този пакет? Защо?_ ______
- _Защо PC0 и PC1 не могат да си говорят без R1, въпреки че са на един комутатор?_ ______

<details markdown="1">
<summary>Отговори за самопроверка</summary>

- Етикет има само на trunk връзката SW0–R1: към R1 – VLAN 10, обратно към SW0 – VLAN 20. На access портовете към компютрите комутаторът премахва етикета.
- Пакетът минава два пъти по една и съща физическа връзка: веднъж в VLAN 10 и веднъж в VLAN 20.
- Не: NAT се прилага само за трафик, който излиза през интерфейса `ip nat outside` (G0/1). Тук пакетът излиза през G0/0.20.
- VLAN 10 и VLAN 20 са отделни broadcast домейни и отделни IP мрежи. Комутаторът (L2) не препраща между тях; нужно е L3 устройство.

</details>
