# D03-11: UDP, TCP и QUIC във Wireshark

> **Поток:** напреднали | **Време:** ~45 мин | **Среда:** Windows 10/11, Wireshark 4.6.x с Npcap, Chrome или Edge
> **Задължителен минимум:** Части 1–3. **Разширение:** Част 4.
> **Връзка с курса:** лекция D01-05 (TCP и UDP портове), D03-06 (TCP), D03-08 (DNS).

## Цели на упражнението

- Сравнение на UDP и TCP заглавките в реален трафик
- Разграничаване на услуги по номер на порт
- Разпознаване на QUIC (HTTP/3) – съвременен уеб трафик върху UDP
- Използване на Statistics → Conversations за сравнение на връзките

## Теоретична основа

| Характеристика | UDP | TCP |
|----------------|-----|-----|
| Установяване на връзка | Не | Да (three-way handshake) |
| Дължина на заглавката | 8 байта | 20–60 байта |
| Потвърждения и повторно изпращане | Не | Да |
| Подреждане на данните | Не | Да |
| Типични услуги | DNS (53), DHCP (67/68), NTP (123), VoIP | HTTP (80), HTTPS (443), SSH (22), SMTP (25) |

UDP заглавката има само четири полета: **Source Port**, **Destination Port**, **Length** и **Checksum**. Надеждността, ако е нужна, се осигурява от приложението.

**QUIC** е транспортен протокол върху **UDP порт 443**, на който работи HTTP/3. Той обединява установяването на връзка и TLS шифроването в една стъпка, затова връзката се отваря по-бързо от TCP + TLS. Загубата на един пакет не спира останалите потоци в същата връзка. Почти цялото съдържание на QUIC е шифровано, но Wireshark може да разчете първите пакети (Initial) и обикновено да покаже името на сайта (SNI). Изключение е **ECH (Encrypted Client Hello)**: тогава истинското име е шифровано и се вижда само външно, общо име на доставчика.

## Част 2: TCP – HTTP заявка

**a.** Стартирайте ново прихващане без capture filter.

**b.** Изпълнете `curl.exe http://neverssl.com`.

**c.** Спрете прихващането и въведете display filter `tcp.port == 80`.

**d.** Попълнете:

| Въпрос | Отговор |
|--------|---------|
| Брой пакети преди първия байт данни (handshake) | |
| Дължина на TCP заглавката в SYN | |
| Дължина на TCP заглавката в пакет с данни | |
| Брой пакети за затваряне на връзката | |

- _Колко пакета общо са нужни за една HTTP заявка по TCP и колко за едно DNS запитване по UDP?_ ______

<details markdown="1">
<summary>Отговори за самопроверка (Части 1–2)</summary>

- UDP заглавката е винаги **8 байта**. Length = 8 + дължината на DNS съобщението.
- При UDP няма пакети за установяване на връзка: запитването е първият пакет.
- TCP заглавката в SYN от Windows е 32 байта (с опции), а в пакетите с данни обикновено 20 байта.
- Една HTTP заявка по TCP изисква поне 3 пакета за handshake, заявка, отговор, потвърждения и 3–4 пакета за затваряне. DNS запитването по UDP е 2 пакета.

</details>

## Част 3: QUIC – уеб трафик върху UDP

> **Предвидете:** Ако отворите https://www.youtube.com в Chrome и филтрирате с `tcp.port == 443`, ще видите ли целия трафик към YouTube?

**a.** Затворете всички раздели на браузъра.

**b.** Стартирайте прихващане без capture filter.

**c.** Отворете в Chrome или Edge `https://www.youtube.com` или `https://www.google.com` и изчакайте зареждането.

**d.** Спрете прихващането.

**e.** Въведете display filter:

```
quic
```

- _Има ли QUIC пакети? Към кой порт и по кой транспортен протокол?_ ______

**f.** Кликнете на първия QUIC пакет с **Initial** в колоната Info. Разгънете **QUIC IETF**, намерете кадъра **CRYPTO** и в него **Handshake Protocol: Client Hello** → **Extension: server_name**.

> Съвременните браузъри изпращат голям Client Hello, който се разделя в няколко Initial пакета. Wireshark го сглобява и показва в последния от тях. Ако не намерите server_name в първия пакет, проверете следващите Initial пакети.

- _Какво име на сайт виждате?_ ______
- _Можете ли да видите адреса на страницата (URL) или съдържанието?_ ______

> **ECH:** Ако в server_name видите име, което не съвпада със сайта (например `cloudflare-ech.com`), а в Client Hello има разширение **encrypted_client_hello**, браузърът използва ECH. Видимото име е само външното; истинското е шифровано. Запишете това като наблюдение – то е правилен отговор.

**g.** Въведете display filter, който показва името на сайта и при TLS по TCP, и при QUIC:

```
tls.handshake.extensions_server_name
```

> **Ако QUIC пакети няма,** причините може да са различни: мрежата блокира UDP порт 443; браузърът използва вече отворена TCP връзка към сайта; HTTP/3 е изключен в браузъра или с политика на организацията; браузърът още не е научил, че сайтът поддържа HTTP/3. Затворете браузъра напълно, отворете го отново и повторете Стъпки b–d. Липсата на QUIC сама по себе си **не доказва**, че UDP 443 е блокиран.
>
> **Резервен вариант:** отворете готовия файл [D03-11_quic.pcapng](captures/D03-11_quic.pcapng) и изпълнете Стъпки e–g с него. Записът е подготвен за обучение и съдържа една HTTP/3 връзка към `www.example.com` (198.51.100.25).
>
> **Разширение:** в **Edit → Preferences → Protocols → TLS → (Pre)-Master-Secret log filename** посочете файла [D03-11_quic_keylog.txt](captures/D03-11_quic_keylog.txt). Тогава Wireshark разшифрова и останалите пакети и ще видите HTTP/3 заявката (GET /) и отговора (200). _Какво трябва да има администраторът, за да види съдържанието на шифрован трафик, и защо в реална мрежа обикновено го няма?_ ______

## Практически съвети за Wireshark

```
udp                                   # Целият UDP трафик
udp.port == 53                        # DNS по UDP
udp.port == 443                       # QUIC (HTTP/3)
quic                                  # QUIC пакети
tcp.port == 443                       # HTTPS по TCP
tls.handshake.extensions_server_name  # Имената на сайтовете (SNI) при TLS и QUIC
udp.length < 100                      # Малки UDP пакети
```

## Заключение

В това упражнение сравнихме UDP и TCP в реален трафик: UDP изпраща данните веднага с 8-байтова заглавка, а TCP първо установява връзка и потвърждава данните. Видяхме, че съвременният уеб трафик все по-често върви по QUIC върху UDP порт 443 и че при шифрован трафик администраторът вижда адресите и портовете, обикновено и името на сайта (освен при ECH), но не и съдържанието.
